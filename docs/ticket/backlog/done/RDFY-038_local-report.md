# RDFY-038 A local report page

## Type
feature

## Risk
low

## Priority
medium

## Status
done

## Owner
implementer

## Background
Everything the operator can currently see is spread across three commands with
console output: `status` for health, `top-played` for the week's most-played
songs, `export-unmatched` for the correction backlog. Nothing shows the chart
playlist at all, and nothing says when a playlist was last updated in a form
you can glance at.

The operator wants one page they can open, on the machine the worker runs on —
a Raspberry Pi they will check the repository out on.

## Scope
- **In scope**:
  - A `report` command writing one self-contained HTML file to
    `storage/report.html`.
  - Three sections: the chart's recent runs; each station's twenty most-played
    songs over the rolling week with play counts; the ten songs most often not
    found.
  - When each playlist was last updated, with date and time, for every station
    and for the chart.
  - A `recent` reader on the sync-run repository, since only the last
    *successful* run is currently retrievable and a failed last run is the more
    interesting one.
  - Recording how many entries a chart page offered, so the report can say
    whether every one of them was found on Spotify. Only the tracks written are
    persisted today, which answers "how many are in the playlist" but not "did
    anything go missing". Added to this ticket after the requester asked for
    exactly that number; it needs one nullable column and a migration.
- **Out of scope (explicit)**:
  - Serving the page, scheduling its generation, or any live refresh. It is a
    file, regenerated by running the command.
  - Serving the page on a network port. The runbook shows a one-liner for it;
    nothing in the project does it.
  - Any change to `status`, `top-played` or `export-unmatched`.

## Constraints
- **Self-contained.** No CDN, no external font, no network at render time: the
  page has to open on a Raspberry Pi with no internet.
- **The file stays out of the repository.** It contains listening history, so
  it is written under `storage/`, which is gitignored — the same reason
  `export-unmatched` output must never be committed.
- **Only configured stations and charts appear.** The database still holds rows
  under station ids retired in RDFY-028; listing them would put a station that
  no longer exists at the top of the not-found table.

## Acceptance Criteria
- [ ] `bun run report` writes `storage/report.html` and prints the path.
- [ ] The page opens with no network access and pulls in no external resource.
- [ ] Each station shows its playlist name, when it was last updated with date
      and time, and its twenty most-played songs of the rolling week with play
      counts.
- [ ] The chart shows its recent runs with date, time, how many entries the
      page offered, how many were found on Spotify, and the error of a failed
      run. A run where the two counts match says so; otherwise it names how
      many were missed.
- [ ] The not-found table lists the ten most frequent entries, and entries
      belonging to a station id that is not configured are excluded.
- [ ] A station with no plays in the window says so instead of rendering an
      empty table.
- [ ] `bun test` passes.

## Verification (manual)
1. `bun run report` → the file is written; opening it offline shows all three
   sections.
2. Disable a station in the configuration, regenerate → it no longer appears.
